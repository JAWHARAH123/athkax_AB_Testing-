# هل عرض تقييمات المستخدمين بجانب المنتجات يزيد معدل الشراء؟

مشروع ختامي في برنامج **التجارب واختبارات A/B والاستدلال السببي (A/B Testing and Causal Inference)**، أكاديمية سدايا، نوفمبر 2026.

- **الاسم:** جوهرة الملحم
- **المنتج:** متجر إلكتروني: صفحة قائمة المنتجات ونتائج البحث

## المشكلة والهدف
يعرض المتجر حاليًا المنتجات في القائمة ونتائج البحث بدون تقييمات، ولا تظهر التقييمات إلا داخل صفحة المنتج. نريد أن نعرف هل يرفع عرض متوسط التقييم (النجوم) وعدد المراجعات بجانب كل منتج نسبة الشراء.

**القرار المطلوب:** هل نطلق عرض التقييمات لكل المستخدمين؟

## السؤال والفرضية
- **السؤال:** هل يؤدي عرض تقييمات المستخدمين بجانب المنتجات إلى زيادة نسبة الشراء؟
- **الفرضية:** إذا عرضنا التقييمات بجانب المنتجات، فسوف ترتفع نسبة الشراء، لأن التقييمات تعطي المشتري ثقة ودليلًا اجتماعيًا وتقلل تردده في الاختيار.
- **المعالجة:** عرض النجوم وعدد المراجعات في القائمة ونتائج البحث.
- **الأثر المتوقع:** زيادة في نسبة الشراء لا تقل عن 0.6 نقطة مئوية.
- **ما يغير رأينا:** إذا كانت فترة الثقة كلها أقل من 0.6 نقطة، أو إذا تجاوز أحد مقاييس الحماية حده المسموح.

## تصميم التجربة
| البند | القيمة |
|---|---|
| المجتمع المستهدف | المستخدمون الجدد الذين يدخلون المتجر خلال مدة التجربة |
| وحدة العشوأة | المستخدم، فيرى النسخة نفسها في كل زياراته |
| المجموعة المقارنة A | الوضع الحالي، بدون تقييمات في القائمة |
| المجموعة المعالجة B | التقييمات بجانب كل منتج |
| نسبة التوزيع | 50% / 50% |
| طريقة التوزيع | دالة تجزئة MD5 على (ملح ثابت + رقم المستخدم)، فالتوزيع ثابت وقابل للتكرار |
| المدة | 14 يومًا (أسبوعان كاملان) |
| شرط SUTVA | قرار المستخدم لا يتأثر بما يراه غيره. الخطر المحدود: مشاركة الأجهزة أو الروابط |

## المقاييس
- **المقياس الرئيسي:** نسبة المستخدمين الذين أكملوا طلبًا.
- **مقاييس ثانوية:** الإيراد لكل مستخدم، وقيمة الطلب لمن طلب.
- **مقاييس الحماية (اختبار عدم الإضرار):** الربح لكل مستخدم (يجب ألا ينخفض)، ونسبة الإلغاء (حد +1 نقطة)، والتواصل مع الدعم (حد +0.5 نقطة)، وزمن تحميل الصفحة (حد +100 ملي ثانية).

## حجم العينة والمدة
- خط الأساس 6%، وأصغر أثر يهمنا 0.6 نقطة (+10% نسبيًا)، ومستوى الدلالة α = 0.05، والقوة 80%، والاختبار ذو طرفين.
- **حجم العينة: 25,737 مستخدم لكل مجموعة**، حسبناه بالصيغة اليدوية لنسبتين وتحققنا منه بمكتبة statsmodels (25,727).
- مع 5,000 مستخدم جديد يوميًا نحتاج 11 يومًا، فقربناها إلى **14 يومًا** لتغطية كل أيام الأسبوع.
- أصغر أثر قابل للاكتشاف خلال المدة 0.50 نقطة. لو اكتفينا بأسبوع واحد يصبح 0.71 نقطة، وهو أكبر من الأثر الذي يهمنا.

## البيانات
البيانات **من محاكاة** (`src/simulate.py`) ببذرة ثابتة، ومحفوظة في `data/dataset.csv`: 70,210 سجلًا، كل سجل مستخدم واحد.

| العمود | الوصف |
|---|---|
| user_id | رقم المستخدم |
| variant | النسخة A أو B |
| day | يوم الدخول في التجربة (1 إلى 14) |
| device / returning | نوع الجهاز، وهل المستخدم عائد |
| pre_orders_90d | الطلبات في آخر 90 يومًا قبل التجربة |
| ordered | هل أكمل طلبًا (0/1) |
| order_value / revenue / profit | قيمة الطلب، والإيراد، والربح بالريال |
| cancelled / contacted_support | الإلغاء، والتواصل مع الدعم |
| page_load_ms | زمن تحميل الصفحة |

**افتراضات المحاكاة:** الأثر الحقيقي للتقييمات +0.7 نقطة، مع زيادة مؤقتة بسيطة في الأيام الأولى (أثر حداثة). قيمة الطلب ترتفع 1.5%، والإلغاء ينخفض 0.4 نقطة، وزمن التحميل يزيد 40 ملي ثانية. وأضفنا 0.3% سجلات مكررة عمدًا لتمثيل إعادة إرسال الأحداث.

**فحوص الجودة:** حذف 210 سجلات مكررة، والتأكد من عدم وجود قيم مفقودة في الأعمدة الأساسية، وفحص SRM، وفحص توازن خصائص ما قبل التجربة (SMD).

## المنهجية
1. **فحص SRM** باختبار مربع كاي، ونوقف التحليل إذا كانت p < 0.001.
2. **المقياس الرئيسي:** اختبار z لنسبتين مع فترة ثقة 95%، ثم **تعديل بالانحدار** (فكرة CUPED) باستخدام الطلبات السابقة ونوع الجهاز ونوع المستخدم، مع أخطاء معيارية متينة (HC1).
3. **المقاييس الثانوية:** اختبار Welch مع **تصحيح Benjamini-Hochberg** للاختبارات المتعددة، وفترة ثقة **Bootstrap** للإيراد لأن توزيعه ملتوٍ.
4. **مقاييس الحماية:** اختبار عدم الإضرار بحدود محددة قبل التجربة.
5. **أثر الحداثة:** الأثر لكل يوم، ومقارنة الأسبوع الأول بالثاني بانحدار فيه تفاعل.
6. **تحليل استكشافي** حسب الجهاز، ولا نبني عليه القرار.
7. **500 اختبار A/A** للتحقق من أن نسبة الإيجابيات الكاذبة قريبة من 5%.

## أهم النتائج
| البند | النتيجة |
|---|---|
| فحص SRM | A = 34,885، B = 35,115، p = 0.39: التوزيع سليم |
| نسبة الشراء | A: 6.02% ← B: 6.62% |
| **الأثر** | **+0.60 نقطة** (فترة الثقة 95%: 0.24 إلى 0.96)، p = 0.001، زيادة نسبية 9.9% |
| مع التعديل بالانحدار | +0.59 نقطة (0.24 إلى 0.95) |
| الإيراد لكل مستخدم | +1.07 ريال (0.35 إلى 1.80)، دال بعد تصحيح BH |
| قيمة الطلب لمن طلب | لا فرق دال |
| الربح السنوي التقديري | +0.49 مليون ريال (0.16 إلى 0.82) |
| مقاييس الحماية | كلها سليمة. زمن التحميل زاد 40 ملي ثانية، وهو أقل من حد 100 ملي ثانية |
| أثر الحداثة | الأسبوع الأول +0.52، والثاني +0.68، والفرق بينهما غير دال (p = 0.66) |
| اختبارات A/A | 5.4% نتائج دالة بالصدفة، قريبة من 5% المتوقعة |

**الأهمية الإحصائية والتجارية:** الأثر دال إحصائيًا، وتقديره يساوي تقريبًا أصغر أثر يهمنا (0.6 نقطة). والأثر الحقيقي المفترض في المحاكاة (0.7 نقطة) يقع داخل فترة الثقة.

## التوصية النهائية
**نطلق عرض التقييمات**، لأن الأثر على نسبة الشراء إيجابي بثقة 95%، والإيراد والربح لكل مستخدم ارتفعا، وكل مقاييس الحماية ضمن حدودها.

**الخطوة التالية:** إطلاق تدريجي (50% ثم 100%) مع مجموعة holdout صغيرة بدون تقييمات لمدة شهر للتأكد من استمرار الأثر، ومتابعة زمن التحميل.

## القيود
- البيانات من محاكاة، والنتائج توضح المنهجية ولا تمثل متجرًا حقيقيًا.
- الحد الأدنى لفترة الثقة (0.24) أقل من 0.6، فلا نستبعد أن يكون الأثر الحقيقي أصغر مما يهمنا تجاريًا.
- تقليل التباين بالتعديل كان صغيرًا (حوالي 1%)، لأن 60% من المستخدمين جدد وليس لهم طلبات سابقة.
- مدة أسبوعين لا تمثل المواسم مثل رمضان والجمعة البيضاء.
- لم نقس أثر التقييمات السلبية على منتجات بعينها، ولا أثر الميزة على البائعين.

## طريقة التشغيل
```bash
git clone https://github.com/JAWHARAH123/athkax_AB_Testing-.git
cd athkax_AB_Testing-
```
